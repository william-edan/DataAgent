# 审计维度
## ✅ 维度 1：语义一致性 (Semantic)

# 判定标准
## 不通过（仅限以下严重问题）
查询了 Schema 中不存在的幻觉字段（表名或列名在 Schema 中找不到）。
完全遗漏了指令中的核心过滤条件（导致数据量暴增，如忘记加时间范围）。
聚合维度与指令要求明显不符（注意：当指令同时要求明细和聚合时，任何合理的折中方案都不算"明显不符"）。
存在明显的 SQL 语法错误（如关键字拼写错误、括号不匹配等）。

**重要提醒**：如果你不确定是否应该判定不通过，请倾向于"通过"。宁可放过一些不完美的 SQL，也不要过度严格导致无法生成可用结果。

## 以下情况不应判定不通过
- 时间戳的实现方式（硬编码 vs 动态函数）
- 时间边界的精确处理（< vs <=）
- 潜在的边界场景（如跨天、跨月）未处理
- JOIN 类型的选择（LEFT JOIN vs INNER JOIN）
- 你认为"可能更好"的替代写法
- NUMBER/INT/BIGINT 类型的时间相关字段（字段名包含 time、date、时间、日期等关键词）使用 Unix 时间戳进行数值比较，这是常见的数据存储方式，不属于幻觉
- NUMBER 类型的非数值语义字段（如 position_name、position_rank、status、type 等）可能存储 ID、编码或枚举值，对其使用 CAST 转换或直接输出都是合理的
- Schema 中字段类型与字段名语义不一致时（如 position_name 类型为 NUMBER），应信任 Schema 定义，不要质疑类型定义的正确性
- 使用 GROUP_CONCAT、STRING_AGG 等聚合函数将明细数据合并到分组结果中，这是解决"既要聚合统计又要展示明细"矛盾的合理方案
- GROUP_CONCAT 可能截断只是潜在风险，不应因此判定不通过
- 使用子查询计算总数或辅助统计是合理的 SQL 技术
- 当指令同时要求"获取明细信息"和"分组统计"时，以下方案均视为正确：
  - 使用 GROUP_CONCAT 将明细合并到分组中
  - 优先满足分组统计，明细信息作为附加
  - 优先满足明细查询，统计作为附加

## 通过
逻辑正确，字段存在。
包含非核心的排序差异（允许）。
包含多余的 ID 列（允许，通常为了后续 Join）。
包含符合业务定义的特定过滤条件（即使指令中未详述，但在 Evidence 中有定义）。
对于"今天"、"昨天"、"本周"、"本月"、"今年"等相对时间表达，以下均视为正确实现：
  - 使用动态日期函数（如 CURDATE()、NOW()、CURRENT_DATE）
  - 使用 Evidence 中提供的具体日期值
  - 使用硬编码的时间戳或日期字符串
  - 两种方式在语义上等价，不应因此判定不通过
  - 对于 NUMBER/INT/BIGINT 类型且字段名包含 time、date、时间、日期关键词的字段，使用 Unix 时间戳（如 1770307199）进行数值比较是合理的，不属于幻觉或未确认的假设
时间边界条件的处理（宽容原则）：
  - 边界运算符的选择（< vs <=，> vs >=）属于业务细节，不应因此判定不通过
  - 只要时间范围能够覆盖目标日期的主要数据，即视为正确
  - 不要纠结时间戳的精确边界（如是否包含00:00:00或23:59:59）
  - 时区差异导致的1天内偏差不应视为错误
  - 使用硬编码时间戳与使用动态日期函数（CURDATE/NOW）是等价的，都应视为正确
  - 日程/事件查询的时间逻辑（完全包含 vs 有交集）是业务决策，不应因此判定不通过
  - 不要假设业务需要处理"跨天"场景，除非指令明确要求
